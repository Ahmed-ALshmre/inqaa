# تصنيف المنتجات وربط البدائل لكل متجر — 6 نوفمبر 2026

صفحة `/product-links` تكمل إدارة الفئات اليدوية في `/product-categories` وبطاقات `/products`. تختار عدة منتجات من متجر واحد، ثم تعدّل الجمهور ونوع القطعة والاستخدام ومجموعة الاقتراح دفعة واحدة. أضيف «تراك» و«دشداشة» كنوعين مستقلين، و«بيتي» و«طلعة / خروج» كاستخدامين؛ بقي «طقم / سوت» مستقلاً عن التراك. الفئات اليدوية التي ينشئها الموظف تبقى متاحة في القوائم.

## طريقة الاستخدام

1. افتح **ربط وتصنيف المنتجات** واختر المتجر. استعمل البحث ومرشحات الجمهور والنوع والاستخدام أو «غير مكتمل فقط».
2. حدد المنتجات المتشابهة فعلاً، مثلاً تراكات ولادية بيتية. «تحديد الظاهر» يحدد نتيجة التصفية فقط، والتحديد يبقى واضح العدد عند تغيير المرشحات.
3. اختر الجمهور والنوع، ثم فعّل تعديل الاستخدامات واكتب مجموعة اقتراح مشتركة. يمكن إنشاء مجموعة بمجرد كتابة اسمها، أو استعمال مجموعة موجودة. القوائم تدعم الإضافة والاستبدال والإزالة؛ الحقول الأخرى تبقى كما هي ما لم تختر تعديلها.
4. افتح اختبار الاقتراح وحدد المنتج والعمر **أو** القياس والاستخدام المطلوب. التجربة تشمل التصنيف المقترح للمنتجات المحددة، حتى قبل الحفظ، وتعرض البدائل المؤهلة دون إرسال أو إنشاء طلب أو كتابة الكتالوج.
5. اضغط حفظ بعد مراجعة عدد المنتجات والتعديلات. كرر للمتاجر الأخرى؛ الروابط لا تعبر بين متجرين. من «تعديل» تستطيع فتح بطاقة المنتج المعني مباشرة.

الصفحة لا تصنف المنتجات الحية تلقائياً حسب تخمين اسم الموديل. يتولى الموظف إدخال التصنيف المؤكد؛ «يومي» لا يعني «بيتي» تلقائياً. يمكن اختيار البيتي والطلعة معاً إذا كانت القطعة مناسبة لهما فعلاً. الأسعار والعروض والألوان والصور والإعلانات والمقاسات والطلبات ومفاتيح AI ليست جزءاً من تعديل الربط الجماعي.

## سلوك الاقتراح

- المجموعة المشتركة أو الربط المباشر يحدد المرشحين، ثم يفحص المحرك المتجر والفئة والجمهور والمقاس أو العمر والتوفر والسماح بالاقتراح. الانضمام إلى مجموعة لا يتجاوز هذه الشروط.
- إذا كانت القطعة الأصلية بيتية، لا يقترح منها قطعة طلعة فقط كبديل افتراضي. الطلب الصريح «للطلعة» يستطيع تغيير الاستخدام. طلب نوع جديد مثل «سوت» يستطيع تغيير نوع البديل صراحةً.
- طلب «تراك ولادي بيتي شتوي عمر 3 سنوات» يجمع الشروط بدلاً من قبول منتج يحقق شرطاً واحداً منها. «غيره» يحتفظ بنوع القطعة والاستخدام والعمر والجمهور في سياق الكتالوج. «طلعة بدل البيتي» يغير الاستخدام مع إبقاء العمر والجمهور والموسم.
- مسار البحث الرئيسي يستعمل التصنيفات أيضاً، حتى لو كان اسم المنتج الداخلي «موديل 22». وصف الموسم المؤكد في بيانات المنتج القديم يظل صالحاً، دون اختراع استخدام بيتي أو طلعة له. المنتج الموقوف اقتراحه يبقى قابلاً للرد عنه عند اختياره مباشرة، ويُستبعد من البحث عن اقتراحات.
- الفئة اليدوية ذات المعرف الثابت تظل قيداً مستقلاً؛ مجرد اشتراك حقيبة وحذاء في مجموعة لا يجعلهما بديلين. سلوك مقاس الحذاء والحقيبة السابق محفوظ.

## التنفيذ والتحقق

`catalog_linking.py` يطبق تحديثاً جزئياً للمنتجات المختارة فقط. واجهتا `classify` و`classify-preview` تشترطان صلاحية إدارة المنتجات ورمز CSRF وبصمة حديثة لكتالوج المتجر. إذا عدّل موظف آخر السعر أو المنتج قبل الحفظ، يُرفض الطلب بـ409 وتُطلب مراجعة القائمة؛ لا تُكتب نسخة قديمة فوق تعديله.

الاختبارات في `account_app/tests/test_product_linking_nov06.py` تغطي المتاجر الخمسة ذات الأكواد المتكررة، ثبات البيانات التجارية، المعاينة بلا كتابة، حقول التحديث المسموحة، صلاحيات الموظفين، CSRF، تعارض النسخ، أوضاع المجموعات، البحث بالتصنيف، وحالات الاستبعاد. `tools/check_product_linking_ui.py` يفحص عشرة سيناريوهات في Edge على الكمبيوتر والموبايل، ببيانات مصطنعة وطلبات Flask معزولة؛ تشمل الحفظ، المعاينة، فتح المنتج، تبديل المتجر، ثبات السعر الأحدث وعدم خروج الصفحة عن عرض الهاتف.

```bash
python -X utf8 -m account_app.tests.run_isolated
python -X utf8 tools/check_product_linking_ui.py
node --check account_app/static/js/product_links.js
node --check account_app/static/js/products.js
node account_app/tests/test_dashboard_ai.cjs
```

نتائج الاختبارات وأمثلة الواجهة الخاصة بالمالك في `outputs/product-linking-nov06/` المتجاهل من Git. لا توجد محاكاة لرسائل زبائن على الإنتاج أو تعديل تلقائي لمنتجاتهم؛ اختبار المحرك والواجهة لا يثبت زيادة معدل الحجز التجاري.
